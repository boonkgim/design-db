02Invariants

What must never be true, taken from the PRD's business rules and journeys. This is the spine of the document: every table, constraint and index below exists to serve one of these, and every one of them is answered in section 6 by a named mechanism. An invariant with an empty last column is one nothing yet enforces.

Write each as a negative statement about state — "no two bookings may…", "no payment may exist without…" — not as a description of behaviour. A rule phrased as a sequence of steps ("when the customer pays, we…") is a journey, and journeys belong to the PRD. The negative form is what can be turned into a constraint; the procedural form cannot.

#Must never be trueFromScopeEnforced by
I1[e.g. a run has more confirmed seats than its capacity, other than by an honoured late payment]PRD §8, FR-12One row, contended DM-3
I2[e.g. a payment exists with no booking, or a confirmed booking with no payment and no credit]PRD §10Two tables, one transaction DM-4
I3[e.g. a credit balance that does not equal the sum of the entries that created it]PRD §8Derived value DM-5
I4[e.g. the same external message applied twice] PRD FR-48One row, idempotentDM-6
I5[e.g. two customers hold the same [unique thing] at the same time]PRD §8Across rowsDM-3
I6[e.g. a booking in a state its history does not justify] PRD §6One row, over timeDM-7

Deliberately not invariants. State these positively — an omitted rule reads as an oversight, and the next person to touch the schema will add a constraint for it.

  • [e.g. Capacity is a soft cap: a payment authorised after its hold lapsed is honoured, so the remaining-seat count is signed and −1 is a legal state, not a bug. PRD §8.]
  • [e.g. Nothing requires an email address to be unique across customers, because the PRD allows a person to book twice with different addresses.]

Every column is NOT NULL unless this document says what its null means. "Not yet paid", "never cancelled", "no note given" are three different meanings and each is written next to its column in section 4. This is the single cheapest rule here: a nullable column with no stated meaning is where an agent will put whatever it has.

Denormalisation ledger

Every stored value that duplicates something derivable is a value that can drift, and each one needs a mechanism that keeps it honest or a stated tolerance for being wrong. Allow at most two or three in the whole schema, and spend them only where a measured query made it necessary.

Decide by direction, not by derivability. "Could this be computed?" settles nothing, because it nearly always could. Ask whether the value must track its source — follow it as the source changes, like a remaining-seat count or a displayed total, which means derive on read — or resist it, staying frozen as it was when the event happened, like the price on a paid booking. Only the first kind is a denormalisation and only it belongs in the ledger below.

[Where a captured value is a computed verdict rather than a copied fact, say what was captured and what was not. Anything re-derivable by a stable function of the stored inputs, or by a lookup keyed off a column already stored, stays derived. Where the logic is fixed and only its parameters tune, capture the parameters — a scalar version key resolving to version-controlled config — and recompute on read: a captured result silently disagrees with a fresh recompute after a parameter change, whereas captured parameters always reconcile. Capture the output only once the logic itself can change past results. Published versions must be immutable; a version key that can be edited under the rows pointing at it is worse than none.]

StoredDerivable fromBoughtKept honest by
[runs.seats_taken][count of live bookings] [the seat claim becomes one guarded statement instead of a count under a lock] [the same statement that changes it, inside the transaction — plus the nightly reconciliation in section 8]

What does not count. A value that cannot be derived is not a denormalisation — the price paid on a booking is not a copy of the workshop's current price, it is a different fact that happens to have had the same value once, and copying it is the only way to keep it true after the catalogue changes. Counting those inflates the ledger and the ledger then gets spent defending them.

06Enforcement map

Every invariant from section 2, and the exact mechanism that makes it impossible rather than merely unlikely. Prefer the lowest level that can express the rule: a type beats a check, a check beats a unique index, an index beats a transaction, and all of them beat application code — because the database is the only layer every writer goes through, including the next agent, a migration, and the operator with a SQL console.

This is the one section where engine-specific names belong. Everywhere else the document is neutral about the store; here it must not be, because "enforced by a constraint" is not checkable and "an exclusion constraint over a range, which needs this extension, which this plan permits" is. Where a mechanism is unavailable, say which rung the rule moves up to.

#MechanismLevelWhat still gets through
I1[The guarded claim in section 9 — one statement whose predicate carries the limit, returning zero rows when it fails. Deliberately not a check on the row, because the cap is soft] [Statement predicate] [Nothing, other than the honoured overage the PRD asks for]
I2[One transaction, plus required references in both directions][Transaction] [A crash between the commit and the external call — handled in section 9]
I3[Not stored at all: the balance is a sum over the ledger][Structural — unrepresentable][Nothing]
I4webhook_events_once — [on PostgreSQL, a unique constraint with an insert that does nothing on conflict] [Constraint][Nothing]
I5bookings_no_overlap — [on PostgreSQL, an exclusion constraint over a time range, which needs the btree_gist extension; if the store lacks it this rule moves up to a transaction and a lock] [Constraint][Nothing while the extension is available]
I6[Application code — the transition table is not enforced by the database][Application] [Any direct UPDATE, including a migration or a console session. Accepted because [reason]; the cost is [what]]

Read the "Application" rows as the risk register for this document. Each one is a rule that holds only while every writer remembers it, and there will be more writers than there are today. Either push it down a level or say in one line why it cannot go lower — "a state machine over four states needs a trigger, and a trigger is harder to reason about than the invariant it protects" is a real answer; silence is not.

Structural beats enforced. The best row in the table above is I3, where nothing enforces the rule because the bad state cannot be written down. Before adding a constraint, spend one minute asking whether the column that could be wrong needs to exist at all — a balance that is always a sum, a status derivable from timestamps, a "primary" flag that a foreign key on the other side would replace.

07Access paths and indexes

Indexes follow queries, and the queries are the PRD's journeys. Every index below names the read it serves; an index that names no read does not get created, because it is pure cost on every write and it will still be there when nobody remembers why.

09Concurrency and transaction boundaries

The rules that only break under simultaneity, and exactly what protects them. Name the contended rows, the order every writer takes locks in, and where the calls to systems we do not control sit — because those cannot be rolled back and therefore cannot be inside a transaction.

Contended thingWho competesProtected byLoser sees
[runs.seats_taken][Two customers claiming the last seat] [A single UPDATE … WHERE seats_taken + :n <= capacity returning zero rows when it fails — no read-then-write, so no lock to hold] [Zero rows updated, and the PRD's "this run just filled" screen]
[A held seat expiring while its payment authorises] [The scheduled job and the webhook] [The webhook re-claims rather than assuming the hold survived; capacity is a soft cap, so it always succeeds][Nothing — the overage is honoured by design]

Isolation level. [The level everything runs at, and the specific rules that need more. Name the anomaly rather than the level: "two concurrent claims could both read the same seat count" is checkable; "we use serializable to be safe" is not. If a rule needs serializable, say what retries the transaction when it is aborted.]

Lock order. [The one order in which writers take locks, so two paths cannot deadlock. If nothing ever holds two locks, say that — it is the better answer.]

Repeat safety. [For every write triggered by something outside our control — a webhook, a retry, a scheduled job that may overlap itself — the column or constraint that makes the second attempt a no-op. This is a schema question, not an application one: it is a unique constraint or it is nothing. Where the key is generated by the application, a retried create collides on the primary key and needs no second mechanism; say so, because it is easy to add one anyway.]

Write order against the outside world. [For every row created alongside something outside the database — an object in blob storage, a file, a provider-side record, an index document — which is written first, and what the failure of the second one leaves behind. Order them so a failure leaves inert garbage: an unreferenced storage object is swept later, whereas an orphaned row is live, appears in listings, and points at nothing. Writing the external thing first requires the id to exist first, which is why this is settled together with DM-1 rather than after it. Name the sweep that reclaims the leftovers and the predicate it runs on — "we would notice" is not a mechanism. Where neither direction is cheap, write the row in a pending state, do the external write, then mark it ready, and sweep the rows that never got there.]
