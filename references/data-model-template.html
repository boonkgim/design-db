02Invariants

What must never be true, taken from the PRD's business rules and journeys. This is the spine of the document: every table, constraint and index below exists to serve one of these, and every one of them is answered in section 6 by a named mechanism. An invariant with an empty last column is one nothing yet enforces.

Write each as a negative statement about state — "no two bookings may…", "no payment may exist without…" — not as a description of behaviour. A rule phrased as a sequence of steps ("when the customer pays, we…") is a journey, and journeys belong to the PRD. The negative form is what can be turned into a constraint; the procedural form cannot.

#Must never be trueFromScopeEnforced by
I1[e.g. a run has more confirmed seats than its capacity, other than by an honoured late payment]PRD §8, FR-12One row, contended DM-3
I2[e.g. a payment exists with no booking, or a confirmed booking with no payment and no credit]PRD §10Two tables, one transaction DM-4
I3[e.g. a credit balance that does not equal the sum of the entries that created it]PRD §8Derived value DM-5
I4[e.g. the same external message applied twice] PRD FR-48One row, idempotentDM-6
I5[e.g. two customers hold the same [unique thing] at the same time]PRD §8Across rowsDM-3
I6[e.g. a booking in a state its history does not justify] PRD §6One row, over timeDM-7

Deliberately not invariants. State these positively — an omitted rule reads as an oversight, and the next person to touch the schema will add a constraint for it.

  • [e.g. Capacity is a soft cap: a payment authorised after its hold lapsed is honoured, so the remaining-seat count is signed and −1 is a legal state, not a bug. PRD §8.]
  • [e.g. Nothing requires an email address to be unique across customers, because the PRD allows a person to book twice with different addresses.]

03Conventions

Decided once here so that section 4 can be read without re-explaining them, and so an agent adding a table later does not invent a second convention beside the first. Each is a real choice with a real alternative; the ones that were close are argued in section 5 rather than settled by this table.

ConventionDecidedBecause
Names[snake_case; tables plural; columns singular; id for the key; <table>_id for a reference] [Folded to lowercase by the engine anyway; mixing the two is the only wrong answer]
Primary keys[bigint generated always as identity / uuidv7] [Which one, against the test in DM-1 — never both in one schema]
Public identifiers[opaque, separate from the key / the key itself] [Whether a row's id may appear in a URL, an email, or an API response]
Timestampstimestamptz, never timestamp; stored UTC; created_at on every table [timestamp discards the offset, and the PRD's [timezone] rule then cannot be evaluated]
Money[integer minor units, with the currency alongside] [Exact arithmetic; the engine's money type is locale-dependent and float cannot represent a cent]
Texttext with a CHECK where a real limit exists; never char(n) [An arbitrary varchar(n) is a production error deferred; a real limit is a business rule and belongs in a check]
Enumerations[lookup table / native enum / check constraint — one rule, and when each applies][See DM-2: the boundary is whether the value is in the customer's vocabulary or only in an engineer's]
Deletion[what is actually deleted, what is superseded by a new row, what is never removed][There is no blanket is_deleted flag — see DM-8]
Nullability[NOT NULL by default; a nullable column must mean something specific, named in section 4] [A null with no stated meaning is a state nobody has designed]

Every column is NOT NULL unless this document says what its null means. "Not yet paid", "never cancelled", "no note given" are three different meanings and each is written next to its column in section 4. This is the single cheapest rule here: a nullable column with no stated meaning is where an agent will put whatever it has.

Denormalisation ledger

Every stored value that duplicates something derivable is a value that can drift, and each one needs a mechanism that keeps it honest or a stated tolerance for being wrong. Allow at most two or three in the whole schema, and spend them only where a measured query made it necessary.

StoredDerivable fromBoughtKept honest by
[runs.seats_taken][count of live bookings] [the seat claim becomes one guarded statement instead of a count under a lock] [the same statement that changes it, inside the transaction — plus the nightly reconciliation in section 8]

What does not count. A value that cannot be derived is not a denormalisation — the price paid on a booking is not a copy of the workshop's current price, it is a different fact that happens to have had the same value once, and copying it is the only way to keep it true after the catalogue changes. Counting those inflates the ledger and the ledger then gets spent defending them.

06Enforcement map

Every invariant from section 2, and the exact mechanism that makes it impossible rather than merely unlikely. Prefer the lowest level that can express the rule: a type beats a check, a check beats a unique index, an index beats a transaction, and all of them beat application code — because the database is the only layer every writer goes through, including the next agent, a migration, and the operator with a SQL console.

#MechanismLevelWhat still gets through
I1[CHECK (seats_taken <= capacity)] … [or the guarded UPDATE in section 9][Constraint] [Nothing, other than the honoured overage the PRD asks for]
I2[One transaction, plus NOT NULL foreign keys in both directions][Transaction] [A crash between the commit and the external call — handled in section 9]
I3[Not stored at all: the balance is a sum over the ledger][Structural — unrepresentable][Nothing]
I4[UNIQUE (source, external_id)] with INSERT … ON CONFLICT DO NOTHING[Constraint] [Nothing]
I6[Application code — the transition table is not enforced by the database][Application] [Any direct UPDATE, including a migration or a console session. Accepted because [reason]; the cost is [what]]

Read the "Application" rows as the risk register for this document. Each one is a rule that holds only while every writer remembers it, and there will be more writers than there are today. Either push it down a level or say in one line why it cannot go lower — "a state machine over four states needs a trigger, and a trigger is harder to reason about than the invariant it protects" is a real answer; silence is not.

Structural beats enforced. The best row in the table above is I3, where nothing enforces the rule because the bad state cannot be written down. Before adding a constraint, spend one minute asking whether the column that could be wrong needs to exist at all — a balance that is always a sum, a status derivable from timestamps, a "primary" flag that a foreign key on the other side would replace.

07Access paths and indexes

Indexes follow queries, and the queries are the PRD's journeys. Every index below names the read it serves; an index that names no read does not get created, because it is pure cost on every write and it will still be there when nobody remembers why.

QueryFromIndexWhy this shape
[The catalogue: live runs, soonest first]PRD §6.1 [(workshop_id, starts_at) WHERE cancelled_at IS NULL] [Equality column first, range second; partial because [n]% of rows are live and the catalogue never reads the rest]
[One customer's bookings, newest first]PRD §6.4 [(customer_id, created_at DESC)] [Covers the list page without touching the table]
[Expire lapsed holds]PRD FR-[n] [(held_until) WHERE state = 'held'] [The scheduled job scans only rows that can expire — a few, not the table]

Free indexes are not free. Primary keys and unique constraints already create one; a foreign key does not, and the delete-time scan on the referenced side is the usual reason to add one. List those separately here so they are not mistaken for query tuning.
