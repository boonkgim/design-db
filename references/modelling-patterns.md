# Modelling patterns

Shapes that hold together, with **what selects each** and **what disqualifies it**.

## How to use this file, and how not to

**This is an elimination aid, not a menu.** Its job is to stop you designing something whose
failure mode is already known, and to stop you rejecting a shape that would have worked. It is
not a list of recommendations, and a model picked from here and justified afterwards is exactly
the failure the skill's _Core principle_ forbids: the invariants decide, not taste, and not a
table.

Use it in one direction only — you have the invariants from section 2, and you are asking which
shapes can still express them. If you find yourself reading it before the invariants are
written down, close it.

Two consequences, both binding:

- **The "disqualifies" line is the load-bearing one.** It is what this file is for. "Selects
  it" is context so the elimination makes sense, not an endorsement.
- **Every shape still has to be argued in the document from the invariants**, with its
  alternatives named. "It is the standard pattern" is not a justification and must never appear
  in a data model document.

**The SQL here is PostgreSQL-flavoured, illustrative, and does not go in the document.** The
dialect is the right one — this repo runs PostgreSQL — but it is here so you can recognise a
mechanism, not to be copied into the data model, which carries semantic types and named
predicates and no engine syntax at all, and no `pgTable` call either. What still needs checking
before a decision rests on it is the _plan_: exclusion constraints, partial indexes, deferred
constraints and generated columns are not all equally available on a managed instance, and
extensions least of all. A mechanism that is not available does not eliminate the pattern; it
moves the enforcement up a level, and section 6 has to say so. A mechanism the ORM's builder
cannot declare moves nothing — the generated migration gets the line by hand — and section 6
says which.

## Identity: what a key is made of

Settle this first. It propagates into every reference and every index, and it is the most
expensive thing in the document to reverse.

### Database sequence (bigint identity)

**Selects it:** nothing generates ids outside the database, no id is ever exposed, and the
smallest key matters — 8 bytes against 16 or 26, repeated in every foreign key column and every
index that carries one.

**Disqualifies it:** anything outside the database is created alongside the row and keyed by its
id (see _Ordering writes against the outside world_); ids are generated by more than one writer,
offline client, or region; a retried create must deduplicate on the primary key rather than
through a separate idempotency table.

**Two things it is not disqualified by**, both commonly claimed: it does **not** cost an extra
round-trip — `INSERT … RETURNING` yields the id with the write, and a parent-child batch threads
through a CTE. And sequence contention is **not** the scaling limit people cite: `nextval()`
takes no row lock, does not roll back, and caches per session. The real contention under heavy
concurrent insert is the right edge of the index — and time-ordered keys share it, so they do
not fix it.

### UUIDv7

**Selects it:** the default for a new schema. Generatable in the application, time-ordered so it
keeps index locality, RFC 9562, stores in a native 16-byte type, and generated in-engine from
PostgreSQL 18. Everything that speaks UUID already handles it.

**Disqualifies it:** creation time must not be inferable — the timestamp is in the leading bits
by construction.

### ULID

**Selects it:** a codebase already uses it, or the id is read aloud, typed by a human, or printed
— the encoding is shorter than a UUID's, case-insensitive, and omits the characters people
confuse.

**Disqualifies it:** the same timestamp leak as UUIDv7. And with no native type it costs 26 bytes
as text everywhere a key appears, which is the trade to state rather than to discover.

**Note before choosing it over UUIDv7 on encoding grounds:** if the driver is that a human handles
the id, the better answer is usually a separate short public reference beside the key. Optimising
the primary key's encoding for humans couples two requirements that are cheaper apart.

### UUIDv4

**Selects it:** exactly one case — creation time must not leak. Randomness is the only way to get
there.

**Disqualifies it:** everything else. Random keys scatter inserts across the index, splitting
pages and missing cache on every write. Choosing it for "distributed uniqueness" when v7 or ULID
would serve is paying that cost for nothing.

## Relationships

### Extension row (a genuine 1:1)

A required, unique reference from child to parent.

**Selects it:** the child is a pure extension of exactly one parent, permanently, and neither is
meaningful alone — a profile hanging off a user, a settings row, a detail table split off for
column width.

**Disqualifies it:** anything that could acquire a sibling. A required unique reference is a
**forced 1:1**: it forbids the parent from existing without the child _and_ the child from ever
having a second. It is written far more often than it is true, because the first write path
really does create one of each and the constraint records that accident as a law.

**The test:** is the child a pure extension of exactly one parent, forever? A user and a profile
— yes. A lead and an assessment — no, because retakes exist the moment anyone asks for one.

### Optional reference on the many side

**Selects it:** the default whenever the forced-1:1 test does not clearly pass. It behaves
identically today — each submit still makes one of each — and it keeps three futures open for
free: retakes and revisions, created-anonymously-then-attached, and records arriving from another
source. Pair it with a delete rule that lets the child outlive the parent where that is true.

**Disqualifies it:** nothing much. The asymmetry is the argument: choosing it up front is free,
and retrofitting it onto a shipped forced 1:1 is a data migration under load.

### Junction table

**Selects it:** _both_ sides are genuinely many, and the link has its own facts — a role, a
quantity, a price, a period. Give it a name from the business and a unique constraint across the
pair, and decide the delete behaviour on both references.

**Disqualifies it:** one side has at most one owner. Then a reference models it and the junction
is machinery that has to be joined through forever for nothing.

## Entity subtypes

### Table per type

**Selects it:** an entity has several types whose fields genuinely differ — payment methods,
authentication methods, document kinds. Each table can then make its own fields required, which
is the entire point.

**Disqualifies it:** the types share nearly all their fields; types are defined by users at
runtime; the row counts are trivial and the query always wants all types together.

### Single table with a type discriminator

**Selects it:** the types share all their fields and differ only in a label, or the set of types
is open and user-defined so no table could be created per type.

**Disqualifies it:** each type has its own required fields. The columns must then all be nullable
so the other types can be stored, which means **nothing is required for anyone** — the invariant
"a card payment must have a last-four" cannot be expressed at all. A conditional check per type
can rescue a small number of these; past a handful it is a table per type wearing a disguise.

### Shared base plus per-type extension

**Selects it:** the types have a real common identity that other tables must reference — one
`payment` a receipt can point at — _and_ type-specific required fields.

**Disqualifies it:** nothing references the base generically. Then it is two tables and a join
you never needed.

## Something finite: seats, slots, stock, licences

### Counter on the parent, changed by one guarded statement

```sql
UPDATE runs SET seats_taken = seats_taken + :n
 WHERE id = :id AND seats_taken + :n <= capacity;
-- zero rows updated means "it just filled"
```

**Selects it:** the units are interchangeable — nobody cares _which_ seat; the count is read on
every page and the read must be cheap; the claim must be one statement so there is no
read-then-write to lock around.

**Disqualifies it:** units are individually identifiable or assignable (seat 4A, licence key,
serial number); anything needs to reference one unit; the count is not the only thing consumed.

**The guard is the pattern, not the atomicity.** An unguarded `count + 1` is atomic and still
oversells: it prevents a lost update but cannot express "and only if there is room". The
predicate in the `WHERE` clause and the zero-row result are what enforce the limit.

**Costs:** the counter is a denormalisation and can drift. It needs a reconciliation, and the
predicate must be written so an intentionally soft cap is not rejected.

### A row per unit, claimed by update

**Selects it:** units are distinguishable, assignable, or must be referenced individually; you
want the invariant to be structural — a seat cannot be sold twice because there is one row and
it has one owner; the number of units is small.

**Disqualifies it:** thousands of units per parent with a hot "how many left" read; units are
created and destroyed constantly; the business genuinely counts rather than allocates.

**Costs:** counting the free ones is a scan or another index; bulk claims lock many rows.

### Exclusion constraint over a range

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (resource_id WITH =, tstzrange(starts_at, ends_at) WITH &&)
  WHERE (state <> 'cancelled');
```

**Selects it:** the conflict is _overlap_, not count — one resource, one period, one claimant.
This is the only concurrency-safe answer to that question, and it is enforced by the engine
rather than by a query that races.

**Disqualifies it:** the store has no exclusion constraints or the plan forbids the extension;
overlap is legal and only the total matters; the "resource" is not a single column.

**Costs:** a GiST index, larger and slower to write than a B-tree; the partial `WHERE` clause has
to be kept in step with the state machine.

## An amount that changes: balances, credit, stock levels

### Append-only ledger, balance derived

**Selects it:** the business must be able to answer _why_ the balance is what it is; money,
credit, or anything auditable; corrections must be visible rather than silent.

**Disqualifies it:** the balance is read constantly and the ledger is long enough that summing
it is a real cost — and you have measured that, rather than assumed it.

**Costs:** every read is an aggregate. Mitigate with a covering index before reaching for a
stored balance; a stored balance is a different pattern with different failure modes, not a
tuning knob.

**Non-negotiable if chosen:** entries are never updated and never deleted. A reversal is a new
entry with the opposite sign, referencing the one it reverses. The moment a ledger row can be
edited, it stops being able to explain itself, which was the only reason to have one.

### Stored balance, guarded

**Selects it:** the balance is the hot read; history is genuinely not required; the update is
expressible as one guarded statement.

**Disqualifies it:** any audit, dispute, or reconciliation requirement — which in practice
means any money. If someone will ever ask "how did it get to this number", this shape cannot
answer.

**Costs:** it is a denormalisation and needs a reconciliation. It also silently loses the
question that produced it.

### Ledger plus periodic snapshot

**Selects it:** the ledger has grown past the point where summing it is acceptable, and you can
point at the measurement.

**Disqualifies it:** you have not measured. This is an optimisation with a whole new class of
bug — a snapshot that is wrong is worse than a slow query — and it is almost never needed at
the volumes a v1 PRD describes.

## A value that changes over time

### Mutable row, no history

**Selects it:** nobody will ever ask what it was before. This is a legitimate and common
answer, and it must be _stated_, because history not recorded cannot be recovered.

**Disqualifies it:** anything financial, contractual, or disputable; anything the operator can
change on a customer's behalf.

### Mutable row plus a history table

**Selects it:** the current value is read constantly and history is read rarely — which is the
usual shape; the questions about the past are known and few.

**Disqualifies it:** the history must be the source of truth rather than a record of it; the
two can disagree, and here they can.

**Costs:** two writes, and a trigger or a discipline that keeps them together.

### Append-only events, current state derived

**Selects it:** the sequence of changes _is_ the domain — a ledger, a state machine whose
history is auditable, a workflow where "how it got here" is a business question.

**Disqualifies it:** ordinary CRUD. This shape makes simple reads expensive and simple
constraints hard to express, and it is chosen far more often than it is needed.

### Validity ranges on the row

**Selects it:** the business genuinely reasons in periods — a price that applies from a date, a
rate valid for a term, an assignment with a start and end.

**Disqualifies it:** you only want an audit trail. Then it is a history table, which is much
simpler.

**Costs:** every query needs the period predicate, and forgetting it returns superseded rows.
Pair it with an exclusion constraint so two rows cannot be valid at once.

### Captured parameters, verdict recomputed

For a value produced by fixed logic over tunable parameters — a score, a tier, a risk band, a
price from a rate card.

**Selects it:** the verdict must be explainable months later, and what changes over time is the
_parameters_, not the logic. Store the immutable input and a **scalar version key** that resolves
to parameters held in version-controlled config; recompute the verdict on read with current code.
One code path, no derived value in the row, and full reproducibility.

**Disqualifies it:** the _logic itself_ can change in ways that would alter past verdicts — then
the output must be captured for rows produced under the old logic, and the version tag says which
logic produced each. Also disqualified where rows must be interpretable without the codebase, or
must survive an edit to config; then the parameters are inlined instead.

**Why parameters beat the result even though both "work":** a captured result silently disagrees
with a fresh recompute the moment parameters change, and anyone reading the raw data reasonably
concludes there is a bug. Captured parameters always reconcile, and they explain the historical
verdict rather than merely asserting it.

**Requires:** published versions are immutable. Never edit a released version's parameters — add
a new version, exactly as with migrations. A version key that can be edited underneath the rows
pointing at it is worse than no version key.

**Encode the pin as a scalar**, not a JSON blob — it must stay queryable and indexable — and not
as parameters copied into every row, which repeats config in the data.

**Never justify any of these by "it saves maintaining code."** It does not: the code that renders
or interprets the captured shape still has to exist and stay compatible with it. The only thing a
capture buys is freedom from keeping every historical version of the logic executable.

## Removal

### Actually delete the row

**Selects it:** the row has no downstream references and no retention obligation; a draft, a
cart, an expired token, a deduplication record past its window.

**Disqualifies it:** anything references it; anything must be recoverable; anything financial.

### A state column

**Selects it:** "deleted" is really a business state — cancelled, archived, withdrawn — with
its own rules about what may still happen to it. This is usually what a soft delete was trying
to be, said honestly.

**Disqualifies it:** nothing, usually. Prefer this over a boolean flag: the state has a name in
the business already, and the flag throws it away.

**Costs, and the one that bites:** every query needs the predicate, and partial indexes on the
live rows make that cheap while making omission visible in the plan. More important, **a unique
constraint now collides with its own dead rows** — soft-delete a user with a unique email and the
next signup on that address fails against a row nobody can see. Either make the uniqueness partial
over live rows, or clear the unique column as part of the removal. This is the most common way the
pattern fails, and it surfaces as an unreproducible signup bug rather than as a constraint error
anyone can read.

### Tombstone: keep the row, destroy the contents

**Selects it:** a deletion obligation for personal data collides with a retention obligation for
the record — the usual case, and the reason a compliance reference with a restrict rule forbids
removing the row at all. The references survive; the personal data does not.

**Disqualifies it:** the obligation is to remove the record itself, not the data in it.

**Costs:** every cleared column must be nullable or have a defined tombstone value, and unique
constraints on cleared columns collide exactly as above.

### Move it to an archive table

**Selects it:** the live table's size is a real problem and archived rows are read almost never.

**Disqualifies it:** archived rows are still referenced by live rows; the schema then has to be
kept in two places, which it will not be.

### The blanket deleted flag

**Never as a default.** Not because hiding rows is wrong, but because applying one mechanism to
every table means no table got a decision. Three of the four options above keep the row exactly
where it is — the question is never "delete or keep", it is which of _delete_, _state_,
_tombstone_ and _archive_ this particular table needs.

## A fixed set of values

### Check constraint over a list

**Selects it:** an internal set, small, changing rarely, with no labels or ordering needed.
Changing it is one statement, and ordinary string operators still work.

**Disqualifies it:** the values need display labels, translations, or an order; other tables
need to reference one.

### A native enumerated type

**Selects it:** the same set is used in several columns or in function signatures, and you want
the engine to reject a typo at parse time rather than at insert time.

**Disqualifies it:** values are removed or renamed with any frequency; the set is
customer-facing and product will want labels; the store does not have the type.

**Costs:** string functions do not apply without a cast, and removing a value is awkward.

### A lookup table

**Selects it:** the values appear in a customer's vocabulary — a dropdown, an API response, an
invoice — or carry anything beyond their name: a label, an order, a validity period, a rate.

**Disqualifies it:** an internal state machine of four values. Then it is a join on every query
for nothing.

**The boundary, stated once:** whether the value lives in the customer's vocabulary or only in
an engineer's. Apply it consistently and say so in section 3, so the next table does not get a
different answer.

## "This already happened"

### A unique constraint on the operation itself

```sql
ALTER TABLE webhook_events
  ADD CONSTRAINT webhook_events_once UNIQUE (source, external_id);
-- INSERT … ON CONFLICT DO NOTHING
```

**Selects it:** the repeat carries an identifier the sender guarantees is stable — a webhook
event id, a message id, a caller-supplied idempotency key. This is the whole mechanism: the
insert and the work happen in one transaction, so a duplicate cannot half-apply.

**Disqualifies it:** the operation legitimately happens twice with identical contents and no
distinguishing identifier. Then the key must come from the caller, and if the caller cannot
supply one, the operation is not idempotent and section 9 has to say what that costs.

**The failure to avoid:** checking for the key, then doing the work, then recording it. The gap
between the check and the record is a race that lets both attempts through. The constraint has
to do the excluding, not a preceding `SELECT`.

**Where a client-generated key already exists**, this comes free: a retried create collides on
the primary key and needs no second mechanism.

### An idempotency key table with recovery points

**Selects it:** one logical operation spans more than one external call, and a retry must
resume rather than restart — a payment that charges, then provisions, then emails.

**Disqualifies it:** a single external call. Then a unique constraint is enough, and this is a
great deal of machinery for it.

**Costs:** every phase boundary is a commit, and the phases must be written so that resuming
from any of them is correct.

**What it requires of the external service:** an idempotency key of its own, derived
deterministically from our stored state, so that a retried call is the same call. Without that,
an indeterminate failure — a timeout — cannot be retried safely, and the model has to record
the uncertainty rather than guess.

### An outbox table

**Selects it:** something outside must happen if and only if the transaction commits — an
email, a webhook, a queue message. The row is written in the same transaction and a worker
sends it afterwards.

**Disqualifies it:** the external call's _result_ is needed to complete the operation. That is
the recovery-point pattern above.

**Costs:** at-least-once delivery, so the receiving side needs a unique constraint of its own.

### External object written before the row

**Selects it:** a row is created alongside something outside the database keyed by its id — an
object in blob storage, a file, a search-index document — and an orphan of that thing is cheap to
sweep while an orphaned row is not. Generate the id, write the external thing, then insert. A
failure leaves an unreferenced object that a sweep reclaims, instead of a live row pointing at
nothing.

**Disqualifies it:** the id is generated by the database, which forces the opposite order; or the
external object is expensive to leave lying around, in which case write the row first in a pending
state, do the external write, mark it ready, and sweep the rows that never got there.

**Not a substitute for the transaction rule:** the external call is outside any transaction
either way. This decides only which direction's leftovers are cheaper to clean up.

## Variable attributes

### Columns

**Selects it:** the attributes are known, and any of them might be filtered, sorted, grouped,
or constrained. This is the default and needs no defence.

**Disqualifies it:** genuinely open-ended attributes defined by users at runtime.

### A JSON column beside the columns

**Selects it:** sparse or caller-defined attributes that are read as a unit and never
constrained; a raw external response kept alongside the normalised fields that were extracted
from it.

**Disqualifies it:** anything filtered or aggregated on regularly — the planner has no column
statistics for it and will guess; anything that needs a foreign key, a unique constraint, or a
required-value rule.

**Costs:** no constraints, no referential integrity, and a schema now enforced in application
code. Every field that graduates to being queried should graduate to a column.

### Entity-attribute-value

**Selects it:** almost nothing, now. It is listed so it can be rejected on the record.

**Disqualifies it:** every query with two predicates becomes two self-joins, and ten becomes
ten. A JSON column does the same job with better ergonomics; real columns do it properly when
the attributes are actually known.

## Embeddings and similarity search

When the product needs semantic search, retrieval-augmented generation, recommendations, or
dedup-by-similarity, the embedding is part of the data model and the shape is tied to what the
managed instance will actually run.

### Vectors in the same database

**Selects it:** the engine has a vector type and an approximate-nearest-neighbour index — on
PostgreSQL that usually means the `pgvector` extension, which is worth confirming on the
managed plan rather than assuming. One
store, one backup, one transaction — the embedding and the row it describes stay consistent, and
a filtered search ("similar, and belonging to this account") is one query.

**Disqualifies it:** the engine has no vector support, or recall and filtering requirements
exceed what an in-database index gives.

**Decide:** whether the vector lives on the source row or in a table beside it — a separate table
keeps a wide, frequently-read row narrow, and lets a re-embedding run without touching the source.

### Vectors in a separate store, joined by id

**Selects it:** the store cannot index vectors at all, or scale demands a dedicated one.

**Disqualifies it:** nothing structural, but it costs the consistency the single-store option
gives: two systems that can disagree, and no transaction spanning them.

**Requires:** a stable id on the relational row that the vector record references, and a written
answer for what happens when one side is written and the other is not — which is the same
ordering question as _External object written before the row_.
